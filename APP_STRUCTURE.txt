The application are structured as:
- index*.html the main files, for test
  the requested libraries are mantained by bower (bower.js and bower_components)
- app tree: the app main tree whith configuration, controller and views (partials)
  - app.js: main js file
  - routess.js: application routes i.e. controller calls
  - configs: configuration file, for test and production
  - controllers: the controllers file: presentation (html) and application (js) layer
  - services: common code: add in placeService.js the functions shared between controllers
  - views: the partials used in controller actions and to reduce presentation complexity
- widgets: the widget tree contain every widget implememntation (see widget tree)
- local_scripts : useful scripts to manage application (for developers)
- server_scripts: server scripts intended as cronjobs (migration, data retrival, etc.)

LEGACY folders:
- css: the old application styles
- img: the old application images
- js: the old application code
- partials: the old application partials (now called views)

Single widget tree.
Everty widget is composed at least by two files:
- widget.json: is the widget definition
  widgets_git2fb.rb script copy those files into the firebase widget node (defined as ckconfig.wdg_url): this file is unuseful until widgets_git2fb.rb are executed (firebase widget node are the information owner), but is necessary to simplify developer work
  The json definition keys are:
  - "id": the widget name (i.e. the widget folder name)
  - "title": the widget title
  - "url": optionally the url on the widget title
  - "urlTitle": optionally the description of the url on the widget title (in parenthesis)
  - "helpDocUrl": optionally the widget doc url (loaded in popup window)
  - "width": the widget width; consider dashboard is vertically divided in 6 comlumns, i.e. the value is at least 1 and at top 6
  - "height": the widget height, calculated in the same way as width
  - "data_bindings": the data loaded and contained by the widget; is an hash, for example:
      - "tide":      {"node_name": "current_tide_level"},
      - "next_tide": {"node_name": "next_tide_peak"}
      where the hask key is the variable name (whith data_ prepended), the node_name hash value is the firebase node loaded (and updated when change) in the variable.
      The example before produce 2 variables; the data_tide variable contain the firebase "current_tide_level" node of firebase defined in ckconfig.dat_url; is han hash and his values can be inserted on HTML code simply adding {{data_tide.tide_level}}; you can use every angularjs instructions in the html
  - "log": true if the widget show a "log" action
  - "log_key": the firebase node where logs are stored; this value are a firebase widget node of firebase defined in ckconfig.log_url
  - "settings": this node contain personalized widget settings (i.e. consider the image url displayed in image widget); is an hash where every hash key is the setting variable name, the "label" hash value is the variable description showed in the widget configuration box, the "value" hash value is the default variable value (stored in user dashboard). A simple example is:
    "imageUrl": {
      "label": "Image Url",
      "value": "https://www.google.com/maps/about/behind-the-scenes/streetview/treks/venice/img/hero.jpg"
    }
